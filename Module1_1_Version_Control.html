🧩 چرا به کنترل نسخه نیاز داریم؟

در حرفه‌ی IT، شما با حجم زیادی از اطلاعات در فایل‌های گوناگون سروکار دارید. اسکریپت‌های خودکارسازی را می‌نویسید که ممکن است در طول زمان تکامل پیدا کنند؛ مثلاً ممکن است قابلیت‌های جدیدی به آن‌ها اضافه کنید، شرایط جدیدی را در نظر بگیرید، یا دامنه‌ی سیستم‌هایی که اسکریپت روی آن‌ها اجرا می‌شود را تغییر دهید.

همچنین فایل‌های پیکربندی مربوط به زیرساخت خود را مدیریت می‌کنید، مانند تنظیمات پیش‌فرض یک برنامه یا آدرس‌های IP اختصاص‌یافته به کامپیوترهای سازمان. این اطلاعات با گذشت زمان تغییر می‌کنند؛ ممکن است الزامات امنیتی افزایش یابد، تعداد سیستم‌ها رشد کند یا نسخه‌های جدید نرم‌افزار مستقر شوند.

📌 در چنین شرایطی، داشتن تاریخچه‌ای دقیق و کامل از فایل‌های پیکربندی و کدهای خودکارسازی برای سازمان بسیار حیاتی است. این تاریخچه به مدیران امکان می‌دهد ببینند چه چیزی و چه زمانی تغییر کرده است — که برای عیب‌یابی بسیار حیاتی است.

علاوه بر این، تاریخچه‌ی تغییرات به‌عنوان یک مدارک مستند عمل می‌کند که به متخصصان آینده‌ی IT کمک می‌کند دلیل وضعیت فعلی زیرساخت را درک کنند. همچنین مکانیزمی برای برگشت کامل یک تغییر فراهم می‌کند، به‌گونه‌ای که نیازی به بازگردانی از روی حافظه نباشد و احتمال خطای انسانی کاهش یابد.

💡 این قابلیت برگشت‌پذیری را در مبحث بازگشت به نسخه‌ی قبلی (Rollback) به‌خوبی درک خواهید کرد.

⚙️ مثال عملی: اسکریپت بررسی سلامت

فرض کنید تیم شما قابلیت جدیدی به یک اسکریپت اضافه کرده است که سلامت تمام کامپیوترهای تحت مسئولیت شما را بررسی می‌کند. این بررسی جدید تأیید می‌کند که سیستم‌عامل پایه (یا همان UEFI) کامپیوتر به آخرین نسخه به‌روز شده است. اما هنگامی که این تغییر را اعمال می‌کنید، ناگهان متوجه می‌شوید که نیمی از کامپیوترها اکنون خطای خرابی نشان می‌دهند.

پس از بررسی، متوجه می‌شوید که این بررسی باید مدل‌های مختلف کامپیوتر را نیز در نظر بگیرد. ممکن است وسوسه شوید که سریعاً کد را اصلاح کرده و آن را به ماشین‌های آسیب‌دیده بفرستید، مخصوصاً اگر راه‌حل به نظر ساده برسد.

⚠️ اما اغلب، تعمیرات سریع خودشان حاوی اشکالات جدیدی هستند، زیرا زمان کافی برای تست صحیح کد جدید صرف نمی‌شود. بنابراین پس از اولین اصلاح، ممکن است مجبور به ارسال دومین یا حتی سومین انتشار اضطراری شوید تا همه چیز واقعاً درست کار کند.

برای جلوگیری از این سردردها، می‌توانید از یک سیستم کنترل نسخه استفاده کنید تا به‌راحتی کد خود را به نسخه‌ی قبلی برگردانید. از آنجا که می‌دانید آن نسخه پیش از تغییر به‌درستی کار می‌کرد، بازگشت به آن نسخه امن است تا زمانی که فرصت پیدا کنید کد را به‌درستی تعمیر کنید، تست‌هایی اجرا کنید و از صحت کار برای همه‌ی مدل‌های ماشین اطمینان حاصل کنید.

✅ با انتشار کد فقط پس از تست‌های کافی، از ارسال اصلاحات پشت‌سرهم جلوگیری می‌کنید. سیستم‌های کنترل نسخه این امکان و بسیار بیشتر را در اختیار شما می‌گذارند.

🔍 ابزارهای diff و patch

پیش از ورود به سیستم‌های کنترل نسخه، بهتر است با دو ابزار ساده‌ی خط فرمان آشنا شوید: diff و patch. این ابزارها پایه و اساس بسیاری از سیستم‌های کنترل نسخه هستند.

  • diff تفاوت‌های بین دو فایل را به‌صورت خط به خط نمایش می‌دهد. برای مثال، اگر نسخه‌ی اول و دوم یک فایل پیکربندی داشته باشید، diff به شما نشان می‌دهد که کدام خط‌ها اضافه، حذف یا تغییر کرده‌اند.
  • patch می‌تواند آن تفاوت‌ها را به‌عنوان یک «وصله» (patch) روی فایل دیگری اعمال کند. یعنی با داشتن فایل اصلی و فایل diff، می‌توانید تغییرات را روی فایل مقصد پیاده کنید.

💡 هرچند در بیشتر موارد مستقیماً از این ابزارها استفاده نمی‌کنیم، اما درک آن‌ها به درک بهتر عملکرد سیستم‌های کنترل نسخه کمک شایانی می‌کند.

سیستم‌های کنترل نسخه از این ابزارها در پشت‌صحنه استفاده می‌کنند تا تغییرات را ذخیره، مقایسه و اعمال کنند. در ادامه با Git آشنا می‌شوید که یکی از قدرتمندترین و پرکاربردترین این سیستم‌هاست.

🐙 Git چیست و چه کاری انجام می‌دهد؟

Git یک سیستم کنترل نسخه‌ی توزیع‌شده است که به شما امکان می‌دهد تغییرات فایل‌ها را در طول زمان پیگیری کنید. با استفاده از Git می‌توانید:

  • تاریخچه‌ی کاملی از تمام تغییرات هر فایل داشته باشید.
  • به‌راحتی به هر نسخه‌ی قبلی برگردید.
  • با چندین نفر روی یک پروژه به‌صورت همزمان همکاری کنید.
  • شاخه‌های مختلف ایجاد کرده و ویژگی‌های جدید را جداگانه توسعه دهید.

Git برای حفظ سلامت کدهای تمام منابع IT ضروری است و امکان همکاری چندین نفر را روی پروژه‌های کدنویسی مشترک فراهم می‌کند.

📌 در این دوره، قدم‌به‌قدم یاد می‌گیرید که چگونه از Git برای پیگیری تغییرات اسکریپت‌ها، فایل‌های پیکربندی و هر نوع سند دیگری که نیاز به ردیابی دارد، استفاده کنید.

ابتدا نگاهی خواهیم داشت به روش‌هایی که افراد معمولاً وقتی از کنترل نسخه بی‌اطلاع هستند به‌کار می‌برند و سپس ابزارهای مرتبط مانند diff و patch را بررسی می‌کنیم. پس از روشن شدن دلیل نیاز به کنترل نسخه، به سراغ نخستین تجربه‌ی عملی با Git می‌رویم.

📥 نصب Git و گردش کار پایه

برای شروع کار با Git، باید آن را روی سیستم خود نصب کنید و نحوه‌ی استفاده از آن را از طریق خط فرمان یاد بگیرید. اگر این کار کمی نگران‌کننده به نظر می‌رسد، نگران نباشید. در این دوره شما را گام‌به‌گام راهنمایی خواهیم کرد و به‌زودی به‌راحتی از آن استفاده خواهید کرد.

💡 Git روی تمام سیستم‌عامل‌های اصلی (ویندوز، مک‌او‌اس، لینوکس) قابل نصب است. برای نصب، می‌توانید از وب‌سایت رسمی Git یا مدیر بسته‌ی سیستم‌عامل خود استفاده کنید.

پس از نصب، با گردش کار پایه‌ی Git آشنا می‌شوید که شامل مراحل زیر است:

  • ایجاد مخزن (Repository) — با دستور git init یک مخزن جدید ایجاد می‌کنید.
  • افزودن فایل‌ها (Add) — با git add فایل‌هایی که می‌خواهید پیگیری کنید را به مرحله‌ی آماده‌سازی (Staging Area) اضافه می‌کنید.
  • ثبت تغییرات (Commit) — با git commit -m "پیام توضیحی" تغییرات را به‌همراه یک پیام توصیفی در تاریخچه ثبت می‌کنید.

این گردش کار به شما امکان می‌دهد اسکریپت‌های خود را تحت کنترل نسخه قرار دهید و از مزایای بی‌نظیر آن بهره‌مند شوید.

🎉 حالا آماده‌اید تا کنترل کدهای خود را در دست بگیرید. در جلسات بعدی، عمیق‌تر با این ابزار قدرتمند آشنا خواهید شد.

🎉 با اتمام این جلسه، شما با اهمیت کنترل نسخه، ابزارهای diff و patch، و مفاهیم پایه‌ی Git آشنا شدید. در جلسه‌ی بعدی، به‌طور عملی وارد دنیای Git می‌شوید.
